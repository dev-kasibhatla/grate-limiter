# Grate-Limiter Project Instructions

## Project Overview

grate-limiter is an anticipatory rate-limit orchestration engine for multi-provider systems.
Monorepo: Rust core + future Python/JS native ports.

## Repository Structure

```
grate-limiter/
├── crates/
│   ├── grate-limiter/          # Core library (Rust)
│   ├── grate-limiter-server/   # HTTP server (axum)
│   └── grate-limiter-simulation/ # Simulation framework
├── python/                      # Phase 2: Native Python port
├── js/                          # Phase 2: Native JS/TS port
├── fuzz/                        # Fuzz testing targets
├── docs/                        # Design docs
└── .github/workflows/           # CI/CD
```

## Coding Style — Rust

- Edition 2024, stable toolchain
- `rustfmt` with `rustfmt.toml` config
- `clippy` with `-D warnings`
- Doc comments on all public items
- Use `thiserror` for error types
- Use `serde` derive for all config/API types
- Prefer `parking_lot` over `std::sync`
- Prefer `DashMap` for concurrent map access
- Use `SmallVec<[T; 4]>` for small collections
- No `unwrap()` in library code (only in tests/examples)
- No `panic!` in library code

## Time & Determinism

- NEVER use `std::time::SystemTime` or `chrono` in core logic
- Always use the `Clock` trait for monotonic time
- All tests must use `MockClock` for reproducibility
- Tests must be deterministic — same inputs → same outputs

## Testing Philosophy

- Unit tests in each module (`#[cfg(test)] mod tests`)
- Integration tests in `tests/`
- Property tests via `proptest`
- Fuzz tests via `cargo-fuzz`
- Benchmarks via `criterion`
- All invariants: health ∈ [0,1], quota remaining ≤ capacity, cooldowns expire

## Concurrency Model

- `GrateLimiter` is `Clone + Send + Sync`
- `DashMap` for provider state (concurrent read/write to different providers)
- `RwLock` for capability lookups (read-heavy)
- `AtomicU64` for counters in quota tracking
- `parking_lot::RwLock` for per-provider health state

## Key Invariants

1. Health score always in [0.0, 1.0]
2. Remaining quota never exceeds capacity
3. Cooldowns always eventually expire (max 600s)
4. Same event sequence → identical routing decisions (determinism)
5. `select()` never mutates state
6. `observe()` is the only state mutation path

## Commit Messages

Use conventional commits:
- `feat:` new features
- `fix:` bug fixes
- `perf:` performance improvements
- `test:` test additions/changes
- `docs:` documentation
- `ci:` CI/CD changes
- `refactor:` code restructuring
